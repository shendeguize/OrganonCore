# Working on Organon Core

Read [PHILOSOPHY.md](PHILOSOPHY.md), including its meanings and limits, before assessing or changing this repository. It is the English authority. [Rationale](docs/rationale.md) explains the philosophy without adding core obligations. Skills implement context-specific methods and may be revised.

For skills applied outside this repository, use [philosophy resolution](skills/references/philosophy-resolution.md) to retain the caller's selected adopted baseline; Core remains the baseline for maintaining this repository. The [document format](skills/references/structure.md) specifies version metadata and stable text-unit IDs as revisable interfaces, not additional philosophical commitments.

For an input assessment, use [organon-core-assess](skills/organon-core-assess/SKILL.md). For philosophical absorption and its necessary synchronization, use [organon-core-absorb](skills/organon-core-absorb/SKILL.md). Read their shared [iteration rules](skills/references/iteration.md) for external grilling, independent-first cross-validation, authorization, records, and stopping. Delegated reviewers return findings instead of recursively requesting review.

Use [organon-core-principled-review](skills/organon-core-principled-review/SKILL.md) for full analysis when its stated trigger conditions apply. It owns the six-dimension method, including bounded review of its own output and criteria. Reuse findings with their standards and grounds; assess owns current philosophical compatibility judgments, while absorb owns philosophical adoption. Method findings do not automatically establish core conflicts, and principled review does not replace independent cross-validation. Routine narrow assessment and wording-only work retain their separate scope.

The initiating agent owns independent skill and documentation maintenance under the shared iteration rules, combining the applicable review skills without treating that work as philosophical absorption. Those rules retain requirements, authorization, actual validation, wording, translation, independent review, and stopping checks. Use external grilling when explicitly requested or needed for material unresolved choices; its absence blocks only the dependent stage.

For repository wording review, use [organon-core-wording-review](skills/organon-core-wording-review/SKILL.md). It checks wording quality only and is also used by `organon-core-absorb`.

Keep changes precise and limited to their authorized scope. Preserve confirmed wording and meaning; a change to a philosophical commitment or its applicability requires the user's explicit decision, even if presented as an explanation. Existing authorization need not be requested again.

For repository text you create or revise and for user-facing replies, use grammatically correct, precise, concise wording that is unambiguous in context. Use terms consistently and make referents, conditions, and scope clear. Remove repetition that adds no information, while retaining necessary qualifications.

Define relevant [validation cases](skills/references/validation.md) before a method change and retain actual results and independent review locally. Update affected documents and links together. Do not represent file checks, agent agreement, or self-application as proof of philosophical correctness.

Keep private inputs and iteration records under ignored `.local/`. The legacy archive is historical, not an active source of obligations. Preserve user configuration and original requirements. The delivered core and skills remain text-only; do not restore the legacy checker or release workflow as part of ordinary maintenance.

For local records, start with `.local/ACTIVE.md`. Keep feedback records active. Exclude `.local/archived/` from default recursive searches and do not open archive packages by default. When the task explicitly requires historical material, consult `.local/archived/INDEX.md` and retrieve only the relevant packages or members, following their recorded dependencies and restoration conditions. Archived decisions are historical evidence, not active obligations; later corrections belong in separate records linked to the originals.

## Remote publication authorization

- Remote publication includes `git push` (branches or tags), release publication,
  PR merges, deployments, and uploads of project artifacts to remote destinations.
- An explicit user request or prior approval authorizes the stated action,
  target, and scope. Reuse that authorization unless withdrawn or superseded;
  do not ask again for the same work.
- General implementation requests, credentials, and tool availability do not
  authorize publication. Approval to push does not by itself authorize a force
  push, merge, deployment, or publication to another target.
- When authorization is missing, first complete authorized preparation and
  relevant checks. Present the reviewable result, exact destination, scope,
  action, and known consequential effects, then request confirmation once.
  Explain that this rule requires authorization for the uncovered publication.
- Execute only the authorized scope. If the action, target, or scope materially
  changes, obtain authorization for that change. Silence is not confirmation.
- Continue authorized preparation and read-only inspection while awaiting a
  decision. This rule does not require confirmation for every remote interaction.
